## Instructions

This exercise begins with a similar setup to the last.

We've got `CreateDataShape` which takes in `TData` and `TError` as arguments:

```tsx
type CreateDataShape<TData, TError> = {
  data: TData
  error: TError
}
```

In the first test we're passing a string for `data`, and `undefined` for `error`.

The test fails because `CreateDataShape` requires two type arguments to be passed in.

### Challenge

Your challenge is to update `CreateDataShape` so that `TError` has a default value. This would allow us to treat it as optional, since the default value would be applied if it wasn't passed a value.

The solution to this challenge is simple, but gives us good insight into some new syntax.

Updating `CreateDataShape` to have `TError = undefined` tells TypeScript that the second argument doesn't need to be passed in:

```tsx
type CreateDataShape<TData, TError = undefined> = {
  data: TData
  error: TError
}
```

If we test our work by creating an `Example` type, we can confirm that `CreateDataShape` works as expected whether we supply one or both arguments:

```tsx
type Example = CreateDataShape<number>
```

### Combining a default value with extends

The default value can be combined with `extends`. For example, we can add an `Error` class:

```tsx
type CreateDataShape<TData, TError extends Error = undefined> = {
```

But then we'd get a type `undefined` doesn't satisfy the constraint `Error` so we can't provide a default that doesn't match the constraint.

A workaround for this is to say that `TError` extends `Error` or undefined equals undefined like so:

```tsx
type CreateDataShape<TData, TError extends Error | undefined = undefined> = {
```

This does start to get a bit messy, so extracting this out to a `MaybeError` is a good way to clean it up:

```tsx
type MaybeError = Error | undefined

type CreateDataShape<TData, TError extends MaybeError = undefined> = {
```

This syntax is useful, but note that similarly to functions, a required type parameter cannot follow an optional one.
